# Phase 4 private structured-job store candidate — 2026-10-21

A separate encrypted SQLite WAL candidate now persists structured-extraction requests and reviewed results. It validates the data-only schema and parser/OCR source units before enqueue, binds idempotency to the owner and exact request, and keeps document text, schema and result behind a per-job envelope key. Existing foreign database files are rejected before mutation. A claim token prevents a stale model response from completing a job after interruption; recovery requires an explicit confirmed interactive-recovery proof and records an interrupted job as failed rather than replaying an uncertain inference call.

The initial focused test failed because the module was absent, then passed after implementation. The tests reopen the database, check owner/scope isolation, inspect on-disk database and WAL bytes for private text, reject changed requests under the same idempotency key, reject incompatible databases, and deny late completion after interrupted-claim recovery.

Independent review found three Important gaps in the first checkpoint. RED→GREEN regressions now hide expired jobs and results, purge expired nonrunning records, and retain an expired running claim until confirmed recovery. Completion accepts raw model candidate text and reruns schema, literal-value and citation checks against the encrypted saved evidence before writing a result; an invented cited value is rejected. Enqueue persists a bounded normalized copy made from validated evidence, so an input `toJSON` method cannot replace the report after validation. These fixes still require full-suite and CI verification at their final source.

The source-only private runner now serializes claims. Its generator calls the existing bounded evidence checker through a supplied qualified inference client, then the store independently reassesses candidate text against its saved evidence before completing the job. A failed or invalid model response leaves the claim running and blocks further runner steps until a separately confirmed recovery marks the interruption. Focused tests cover successful persistence, two simultaneous steps, a model failure and a fabricated citation. The disposable Debian model proof used the real local model and shared interactive lease on a fixed English/Arabic invoice. It found the invoice ID, date and total with exact source citations, persisted the checked result, reopened the encrypted queue and recovered the same result. The deployed gateway PID stayed unchanged and the host used zero swap. This is one synthetic quality case, not broad accuracy qualification.

At source `e33c32c`, Windows passed 279 tests with 40 Linux-only skips; a fresh Debian checkout passed 319/319, the real-model persistence proof and documentation checks passed, and both required GitHub CI jobs passed.

There is no supervisor connection, HTTP route, installed service, cancellation or backup integration. The separate database requires coordinated backup, restore and deployment before activation. Full model quality and Phase 4 release gates remain open.

An additional source test aborts an active generator, checks that its claim remains running and that the runner refuses another step until explicit recovery. At `a332539`, a disposable Debian process-crash test killed a child after it claimed a synthetic encrypted job, reopened the queue, rejected an unconfirmed recovery and then recorded a visible interruption. This checks SQLite claim durability and late-replay blocking; the test's final recovery confirmation is injected and does not qualify the real offline lease-recovery procedure. The live gateway/chat/embedding PIDs and package-status digest remained unchanged. ## Private supervisor queue boundary — 2026-10-22

The inactive document supervisor opens the separate structured SQLite WAL store with its existing vault and accepts bounded `submit-structured` and `structured-status` commands over its permission-restricted Unix socket. The caller supplies the already authenticated namespace and scope. The queue validates schema and source evidence again; duplicate requests return the same job, and foreign owners/scopes cannot read it. A Linux socket test closed and reopened the store and socket, then recovered the queued receipt. On the disposable Debian LXC, a source-only supervisor process accepted a structured request, returned scoped status, stopped cleanly, and left the encrypted job readable after reopen. The gateway/chat/embedding PIDs and package-status digest stayed unchanged. This did not install or activate a Phase 4 service.

The supervisor service remains isolated from network and model credentials. Its queue is deliberately not consumed inside that sandbox. The separate model runner has not been connected to the supervisor, so these jobs remain queued until an inference bridge, cancellation, lease recovery and coordinated backup/restore are qualified. The public gateway has no structured-extraction route. Full suite and CI results for this checkpoint are recorded in progress tracking after verification.

Focused review found that an existing vault and document DB could start with a missing structured DB, silently replacing lost structured jobs with an empty queue. The disposable native restart proof first failed on that condition, then passed after startup required all three state files to exist together or all three to be absent for first initialization. A future migration from an older document-only state must be an explicit, separately reviewed operation; this source-only Phase 4 service has never been installed on the live host.

The same committed source was staged temporarily under `/opt/localai/documents/candidates/` and started as a transient systemd unit with the candidate unit's actual user/group, private network, inaccessible model/credential paths, read-only system, 256 MB memory limit and zero-swap limit. The `localai` service account used the private client to submit an idempotent structured request and read scoped status; another owner received no job. After stopping the unit, the root proof reopened the encrypted store and found the queued job. The synthetic unit/state and temporary staged source were removed. The live gateway/chat/embedding PIDs and package database did not change. This qualifies the inactive queue transport under the intended sandbox, not installed operation or model execution.

The source-only runner now awaits asynchronous claim and completion operations and rechecks its recovery barrier and cancellation signal after a remote claim and before completion. RED→GREEN regressions catch treating a Promise as a job and reaching generation after cancellation during a pending claim. A prototype queue-wide claim/complete socket exchange passed synthetic tests, but independent review found it exposed the next owner's decrypted report and claim token to any process with `localai` socket access. Those socket operations and their synthetic proof changes were removed before commit. A future executor needs an owner-bound claim or separately protected capability, plus the real lease/restart/cancellation proofs. Existing submission/status remains the only structured socket interface.

## Receipt-bound executor candidate — 2026-10-22

The next private candidate implements a claim for one known receipt. Enqueue derives a purpose-separated, 256-bit HMAC capability from the vault and exact job identity; it is returned only with the first internal enqueue receipt, never with an idempotent replay or ordinary status. The `claim-owned-structured` socket command requires that capability plus the job ID, namespace and scope. Wrong owner, scope, capability or ID returns no claim. Review found an unrestricted queue-wide method still present on the store itself; it was removed, and the source-only runner is now bound to one exact receipt. Completion still requires the random claim token and reruns the citation/literal checks against the encrypted saved evidence. A Linux socket test used the asynchronous runner across that boundary; the owner saw the persisted result while another owner did not. A transient systemd unit under the candidate restrictions repeated claim and completion as the `localai` account and reopened the encrypted result after stopping. Synthetic state, unit and staged source were removed; live services and package inventory were unchanged.

The capability is an internal executor secret. Any future public route must remove it from HTTP responses and retain a crash-safe way to schedule known receipts; a lost receipt cannot recover its capability by replaying enqueue. The restricted-service proof uses a synthetic model candidate, not the actual llama.cpp model or interactive lease. Recovery, cancellation, sustained load, coordinated backup and whole Phase 4 gates remain open.

After removing the unrestricted store method, the disposable child-SIGKILL proof still recovered a claimed job only after explicit confirmation. The direct source-only runner repeated its separate real llama.cpp invoice proof using the receipt-bound claim, finding invoice ID, date and total with saved citations and zero swap. That direct proof is not the restricted-service socket proof; a protected receipt handoff and real lease ownership across the socket remain unqualified.

## Full-window interactive lease candidate — 2026-10-22

The source-only runner can now take an interactive admission that covers the claim, model request and result commit in one lease. A failed admission makes no claim and leaves the receipt retryable. A lost lease after claim prevents completion and leaves the runner blocked for explicit recovery. During a granted lease the recovery marker is intentionally present, so the runner checks the barrier before admission and uses the lease signal during work. The lease client's completed exchange confirms release; a separate barrier check afterward would race a new lease. The first Debian real-model run exposed the active-marker interaction; a failing regression reproduced it before the correction. The disposable real llama.cpp invoice proof then passed with the outer lease, cited ID/date/total, encrypted reopen and zero swap, without changing the gateway process.

This is a direct source-only proof using the real local model. It has not yet exercised a separate protected executor receiving receipts across the supervisor socket, installed crash recovery, coordinated backup or the full Phase 4 release gates. No public route or document service was activated.

## Privileged pending-receipt recovery candidate — 2026-10-22

The root-owned structured store can now enumerate a bounded set of unexpired queued receipts and rederive their capabilities from the existing vault after reopen. The method returns job ID, namespace, scope and capability only; it neither decrypts report content nor returns a claim token. It is not wired to the group-accessible supervisor socket or any HTTP route. A RED→GREEN unit test confirmed reconstruction across reopen while omitting expired and running jobs. A disposable Debian child-SIGKILL proof kept one job running and another queued: after restart, the running claim still required explicit recovery, while the queued receipt was reconstructed and completed with source-checked evidence. Live services and packages were unchanged.

The root process still needs a protected, crash-safe way to hand each recovered receipt to a separately sandboxed executor and to schedule it without losing or duplicating work. This store enumeration alone does not meet that release gate.

## Isolated receipt-socket candidate — 2026-10-22

A separate private Unix socket now serves at most one queued receipt per request from the root-owned store. Its parent must be owned by the supervisor user and the configured executor group with mode 0750; the socket is mode 0660. The fixed request does not accept a namespace, job ID or arbitrary command. It withholds receipts while the interactive recovery barrier is set or shutdown has begun. No report plaintext, claim token or result crosses this socket. The group-accessible document socket remains unchanged and has no queue-enumeration operation.

A disposable Debian proof used `nobody`/`nogroup` as a stand-in for a future dedicated executor account. That account received only the receipt; the deployed `localai` account could not traverse the socket directory and received `EACCES`. The proof used synthetic state under `/tmp`, removed it afterward, and did not install a service or change live Phase 3 processes. A dedicated account/unit, credential access, receipt consumption under the real lease, crash/restart scheduling and complete release gates remain open.

Independent review found that the first socket candidate allowed unlimited idle clients. A failing saturation test reproduced the condition; the socket now caps clients at two. Follow-up review found that a half-open peer could keep a slot after a valid reply; a second failing test reproduced it, and the server now closes the connection after flushing its reply while retaining the deadline until close. Tests also confirm the recovery barrier and shutdown withhold receipts. The candidate still requires an isolated production executor group distinct from `localai` before wiring.

A source-only adapter prototype joined the reconstructed receipt socket to owner-bound claim/completion on the existing document socket and passed a one-process integration test. Independent review found that an in-flight remote completion could still commit after the interactive lease was lost, because the supervisor has no server-side lease binding at commit. The test also concealed the access problem: a dedicated executor can reach its isolated receipt socket but cannot reach the existing `root:localai` document socket without joining the broader `localai` group. The adapter and test were removed before commit. A server-validated lease/claim contract and a narrow executor claim channel are required before this handoff can be integrated.

The implementation uses SQLite's online backup on the open WAL connection, checks schema identity and full integrity on the copy, reserves a fresh owner-private destination, and removes failed copies. The focused test restores committed work using the same vault, rejects overwrite and source replacement, and rejects a world-writable destination directory on POSIX. This does not include the vault key or coordinate the document/account stores, so it is not a qualified backup or restore gate.

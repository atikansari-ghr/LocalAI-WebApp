# Phase4 private job-store checkpoint — 2026-10-19

The internal document job store is a separate SQLite WAL database in a private directory. It does not migrate or touch the enrolled account database. The uploaded name, MIME, bounded bytes and result are AES-256-GCM ciphertext under a random per-job key sealed by the existing vault; ID, namespace, status and timestamps remain visible metadata. Tests reopen the store, verify namespace isolation, check database/WAL files for plaintext, reject a wrong vault key and oversized result, and prove an active claim is not reassigned after restart.

Cancellation of an active claim enters a nonpurgeable `cancelling` state until a worker token confirms cleanup. Interrupted claims likewise require an explicit native-cleanup confirmation before they become failed. The store does not itself stop a systemd unit or accept that confirmation from an HTTP caller; that supervisor integration is a separate mandatory gate. There is no public route or active phase4 worker.

The first restricted Debian unit ran4/5 tests. The remaining case created a fixture database with ordinary SQLite permissions, which was correctly rejected as unsafe before the intended incompatible-schema assertion. After fixing the fixture's mode,5/5 passed. Independent review then reproduced an unrelated version-1 SQLite database being modified on a mistaken path. A distinct SQLite application ID and exact schema check now run read-only before any writable open; the regression confirms the foreign file remains byte-for-byte unchanged. The corrected restricted DynamicUser/PrivateNetwork/private-devices/private-temp/protected-filesystem unit passed6/6 with256MiB memory cap, zero swap and39.6MiB observed peak. Independent re-review found no remaining Important/Critical issue. The enrolled gateway and account state were not changed. Whole-phase qualification, backup/restore, retention under load and native supervisor cleanup remain pending.

The draft document API contract then required binding each persisted job to its access scope, operation and idempotency key. Tests first observed cross-scope reads and duplicate submissions, then verified the corrected namespace/scope checks and exact request replay behavior. Reuse after expiry is allowed only after an inactive job can be removed; an expired running claim remains protected until cleanup. Review found the initial unkeyed request fingerprint permitted offline guesses of document content from the encrypted database. Reproduced YES/NO and key-guess tests now require purpose-separated vault-keyed HMAC fingerprints instead. The changed candidate schema has never been deployed as a service or used for enrolled data. Its restricted Debian unit passes9/9 with zero swap and40.4MiB peak. Independent re-review found no remaining Important/Critical issue. Full-source/CI results are separate subsequent gates.

The one-shot worker follow-up exposed an unsafe finalization call shape: a store caller could mark a claim complete or cancelled before confirming that its native unit had stopped. A regression first reproduced premature completion, then `complete` and `finishCancellation` were changed to require explicit native-cleanup confirmation. Rejected finalizations retain the active claim. The restricted Debian job-store tests pass10/10 with zero swap and40.1MiB peak; independent review found no new issue. This is a trusted internal supervisor assertion, not proof supplied by an HTTP caller. The final supervisor must verify unit exit before passing it.

A later job-store candidate adds failure finalization for a stopped worker. It requires the live claim token and trusted native-cleanup confirmation, accepts only bounded document error codes, persists a failed status across reopen, and refuses to overwrite a cancellation or completed claim. Two RED→GREEN regressions cover claim binding, validation and cancellation races. Focused tests pass12/12, full Windows223plus3POSIX skips and Debian226/226 pass, and independent review found no high-priority issue. The root supervisor still must provide actual cleanup evidence before using this method; a Boolean supplied by arbitrary code is not itself a proof.

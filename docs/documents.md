# Document processing development

Document processing is under development on the phase4 feature branch. It is not exposed by the deployed gateway and the OCR/format phase gate has not passed. The live service remains the qualified phase3 preview.

## Current internal contracts

`inspectDocument({name,mime,bytes},limits)` performs preliminary name/extension/MIME/magic/UTF8/size inspection and returns frozen metadata with the exact SHA256. It does not validate PDF/image structures or archive/container entries. Those results explicitly say requires-parser-validation or requires-container-validation; no caller may interpret them as authorization to extract or process the container. Unknown types and malformed names are rejected. Filename metadata is never a destination filesystem path. Supplied MIME parameters are normalized and checked against the extension's explicit list.

Implementation defaults are10MiB per input and1MiB for UTF8 text. Server-side limits may be reduced; internal overrides are bounded to50MiB and are not public request settings. Shared-memory input views, invalid UTF8, NUL-containing text, path/stream filenames and recognized binary content disguised as text fail. Original upload bytes are unchanged. These defaults are implementation choices, not newly recovered user decisions.

`parseTextDocument` currently supports TXT,Markdown,JSON,CSV andICS only. It returns literal text, frozen source units and a parser identity. Source start/end offsets are zero-based UTF16 indices in the decoded source text, end-exclusive; line/row/column numbers are one-based. UTF8 BOM handling follows TextDecoder, so offsets are not byte offsets in the original file. This contract must remain explicit in later field citations.

- TXT/Markdown preserve literal source, including markup; they do not render HTML or follow links.
- JSON validates syntax and bounds nesting to32 and values to10000; original members remain literal, including duplicate-key evidence. It does not silently turn duplicate keys into selected extracted fields.
- CSV supports quoted delimiters/newlines and escaped quotes, preserving per-cell row/column and original source spans. Formula-looking values remain literal text. Column count is bounded to256.
- ICS unfolds continuation lines and checks balanced bounded components and the VERSION:2.0 calendar envelope. It returns literal calendar content and physical source ranges. It does not resolve URLs, apply timezone/recurrence semantics, validate proposed event fields or create events in any calendar.

Units are capped at10000 and each decoded line/cell at65536UTF16 units; extraction output remains bounded by the text-byte limit. Invalid/unsupported parser requests return safe typed DocumentError codes without echoing document content. parseTextDocument rejects HTML/XML; their separate internal markup parser is described below. EML,PDF,rich Office/OpenDocument/legacy formats,images and ZIP remain unavailable to extraction until corresponding isolated structural parsers are implemented and qualified.

`parseMarkupDocument` now adds internal HTML/XML extraction using a separate locked pure-JavaScript parser cohort. htmlparser2 12.0.0 (MIT) decodes entities, keeps inline text continuity and omits script/style/template and active embedded content. It reports source-text spans and warns that source order is not rendered page layout. It never fetches links, images, frames, stylesheets or scripts. saxes6.0.0 (ISC) validates XML namespaces/well-formedness before text scanning; DTDs are forbidden and external entities/XInclude are never resolved. XML citations preserve exact decoded-source spans and indexed element paths, including CDATA. Markup depth32, nodes10000 and attributes256 are enforced. This is internal parser development, not live document API availability or full phase4 acceptance; email/containers/PDF/images remain pending. Prefix installation is documented in the installation guide and CI.

## Bounded ZIP inspection checkpoint

`readZipDocument` validates generic ZIP containers in memory, without writing extracted files. Defaults:100 entries across nested archives,10MiB per member,50MiB total expanded bytes,100:1 compression ratio,two nested archive levels and a10second shared deadline. Trusted callers may only reduce these limits. Stored/deflated ZIP2.0 records require matching local/central headers, exact expanded sizes and CRC32; encrypted, spanned, ZIP64 and unsupported codecs are rejected. Paths are normalized and checked for traversal, aliases, file/directory collisions, links and special/executable files. Cancellation is shared across nested reads.

Returned member bytes still require their own format parser and authorization. This checkpoint does not accept Office containers, expose an upload route or qualify the full document phase. Archive entry/source hashes describe exact bytes; no extracted member name is used as a filesystem path.

## OOXML package policy checkpoint

`inspectOfficePackage` adds internal DOCX/XLSX/PPTX package checks before text extraction. The same ZIP limits/CRC/path/cancellation checks apply; relationship parts are allowed only through the Office profile and nested ZIP packages are rejected. It validates bounded well-formed namespace-aware XML without DTDs for every XML/relationship part, requires content type declarations and one package-level main document relationship, and checks the selected main part's declared type/root namespace against the filename family. Internal relationship targets must resolve to existing package parts. External relationships, macro/ActiveX/OLE/embedded object indicators and unsupported executable members fail closed.

This intentionally restrictive first profile rejects external hyperlinks as well as linked templates/assets; it does not fetch them. Supported profile currently uses the transitional2006 namespaces, UTF8 XML and the ZIP2.0 subset. Full OOXML schema validation, strict namespaces, Office text/tables/cell/slide extraction, media validation and isolated public worker exposure remain pending. A policy-passed result does not claim complete Office support or safe rendering. Returned original member bytes still need their own format validation.

Package identity follows the official [Microsoft package construction guide](https://learn.microsoft.com/en-us/office/open-xml/general/how-to-create-a-package): package main-part relationships and document type must match. Exact source hashes are preserved; no archive members are written to disk.

## Word main-body text checkpoint

`parseWordDocument` now performs internal DOCX main-body literal extraction after package policy validation. It follows namespace-aware paragraphs/runs/text, preserves multilingual text/entities/CDATA, outputs tabs/explicit breaks and paragraph boundaries, and includes part SHA256, indexed XML path, paragraph/run numbers and exact UTF16 decoded-XML spans for text. Structural tab/break units explicitly use element provenance without fabricated character offsets. Original upload/member bytes remain unchanged.

Deleted/moved-from text, field instructions, foreign namespace markup and embedded stories such as drawing textboxes are omitted with warnings; directly hidden runs are omitted while explicit false flags are honored. Cached field results are not recalculated. Styles, inherited visibility, numbering/list labels, page layout, table geometry/merged cells, headers/footers/notes/comments and other stories are not reconstructed. Main-body source order is not a claim of rendered visible page text. Full OOXML schema validation remains pending. Source citation conventions refer to decoded XML rather than offsets into ZIP bytes.

The API accepts only decreasing output limits up to1MiB and shares archive cancellation/deadline checks, enforcing a total processing deadline. It remains an internal parser without public document routes or live gateway deployment. Word's paragraph/run/text hierarchy is documented by [Microsoft](https://learn.microsoft.com/en-us/office/open-xml/word/structure-of-a-wordprocessingml-document).

## Spreadsheet and slide literal extraction checkpoint

`parseSpreadsheetDocument` now follows workbook sheet relationships and extracts XLSX shared/inline strings, raw numeric/boolean/error/date/string values and literal formulas. Cached formula values are explicitly marked; missing caches return inert formula text and a warning. No expression, URL, macro or recalculation is executed. Cells include sheet/name/id, row/column/address, exact part hash/XML element citation and original value/formula source spans, including shared-string provenance. Invalid/duplicate/out-of-range or unordered coordinates, unresolved strings, unsupported shared/array formulas and wrong relationship kinds are rejected. Styles/date formatting, charts, comments, merged-cell geometry and rendered display are not inferred. Hidden sheets/rows may be included with warnings.

`parsePresentationDocument` follows presentation slide-list relationships rather than filenames, extracting namespace-aware shape text and grouped-shape paragraphs in source order. Exact XML spans/part hashes and slide/id/shape/paragraph identifiers are retained. Direct hidden shapes are omitted; hidden slides are included with a warning. Notes, masters, media, tables, rendered positioning and custom show selection remain unextracted. Cached field text is not recalculated. Global1MiB output and10000reference limits include slide separators and span all selected parts; ZIP/XML/deadline/cancellation limits remain enforced.

Official references: [spreadsheet cell values](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.spreadsheet.cellvalue) and [presentation text/slide-list relationships](https://learn.microsoft.com/en-us/office/open-xml/presentation/how-to-get-all-the-text-in-a-slide-in-a-presentation). These are internal extraction APIs; no live/public document support is claimed.

## Email literal extraction checkpoint

`parseEmailDocument` uses the locked postal-mime4.0.11 (MIT-0) cohort for charset-aware RFC822/EML input. Preliminary EML inspection now allows8bit mail bodies while rejecting recognized binary signatures/NUL; text-only parsers still reject EML. Input remains bounded to10MiB. The parser applies16MIME levels,100parts,64KiB cumulative headers,20attachments/10MiB decoded attachment total,1MiB text output, an elapsed10second check and caller cancellation. Hard termination and worker isolation remain required before public exposure.

It returns decoded subject and literal plain body, or inert HTML-to-text without returning executable HTML or fetching remote content. Nested messages are attachments and are not recursively scanned. Decoded sender metadata is not authenticated. Unsafe attachment names become synthetic labels; names are never paths, attachments remain unvalidated, and no calendar/application actions run. Top-level encrypted/S-MIME messages are explicitly unsupported.

Email provenance binds the original upload hash but intentionally supplies no invented raw byte spans for MIME-decoded/aggregated body content. Plain line endings/trailing newlines follow postal-mime normalization. Attachment hashes identify MIME-transfer-decoded content; text/calendar and application/ics are explicitly labelled normalized UTF8 calendar content because the library transforms their bytes. Raw MIME attachment-byte preservation requires a later raw-part mapping, not a claim this API makes. Subject/body/name values remain untrusted for any future UI rendering. This internal API has no live public route. Dependency behavior and bounds follow the [official postal-mime documentation](https://github.com/postalsys/postal-mime).

## OpenDocument literal extraction checkpoint

`parseOpenDocument` adds restricted ODT/ODS/ODP package and literal-content parsing. It checks the referenced first ZIP member is stored mimetype at offset0 without local extras, exact MIME bytes, required content/manifest, root media agreement and declared members. All XML uses bounded namespace-aware parsing without DTDs; encryption, scripts/forms/embedded objects and external links are rejected. Referenced local assets must exist and still require separate binary format validation. Manifest directories and uncommon package profiles may be rejected; full ODF schema compatibility is not claimed.

ODT preserves paragraph/heading/inline text, explicit spaces/tabs/breaks with XML spans or explicit element provenance. ODS bounds aggregate repeated rows/cells to10000, keeps literal formulas/raw caches without executing them and records sheet/row/column/part identities. ODP keeps page source order and paragraph citations. Annotations/notes/revision definitions, styles, fields, list labels, layout and media interpretation are omitted or not resolved, with warnings. No rendered visual fidelity or public route is implied. Global output/citation/deadline/cancellation limits remain in force. Package rules follow [OASIS OpenDocument1.3 packages](https://docs.oasis-open.org/office/OpenDocument/v1.3/OpenDocument-v1.3-part2-packages.html).

## PDF native candidate checkpoint

The private Debian13 candidate uses Poppler25.03.0 (Debian25.03.0-5+deb13u4); services/documents/poppler-packages.json records exact downloaded package bytes/SHA256/version/architecture and vendor copyright paths. Packages were downloaded and extracted privately, not installed into the active host. Vendor licenses remain with the candidate; Poppler is a separate native tool, not an unlicensed JavaScript dependency. No PDF worker is enabled by this checkpoint.

`createPdfParser` uses fixed operator tool/library/font paths, private temporary files, literal arguments without a shell, bounded stdout/stderr, cancellation, process-group termination and a shared30second processing budget. Metadata limits100pages; layout decoding keeps native word boxes in top-left PDF points and enforces coordinate/output/image budgets. Native/bitmap/mixed/empty statuses describe observed native text and bitmap images, not visual completeness: vector diagrams are not detected by bitmap inventory. Explicit rasterization therefore covers every page, including native-text pages, up to2000pixels on the longest edge and20MiB aggregate PNG output. Encrypted or JavaScript-enabled PDFs fail closed; native warnings/annotations/embedded files and visual interpretation are not a claim of complete content extraction.

Only the exact known Poppler XHTML doctype is removed from its output; other DTDs are rejected without network resolution. Native text spacing is reconstructed from words, not raw PDF bytes. Original upload hash, one-based page and coordinates bind citations. Raster hashes identify rendered PNG bytes. Actual execution requires the tested nonroot systemd sandbox with network/private devices, inaccessible live state/models, CPU/memory/zero-swap limits and controlled worker admission before any public route. The factory itself does not install this sandbox. Synthetic PDF fixtures contain native/scanned/mixed pages, an encrypted counterpart and truncation; their preview pages were visually checked. The fixture generator uses bundled ReportLab4.4.9/pypdf6.10.0; encrypted output is randomized.

## Image normalization native candidate checkpoint

`createImageNormalizer` uses a fixed offline Pillow13.0.0 worker from the previously hash-locked Python candidate. The verified [PyPI release](https://pypi.org/project/pillow/13.0.0/) declares MIT-CMU and Python>=3.11; actual target CPython3.13.5/Pillow13.0.0 runs are recorded separately. PNG/JPEG/WebP/classic TIFF are verified and decoded under the same private native sandbox before OCR. Limits are20MP/frame,40MP aggregate input pixels,100frames,20MiB aggregate PNG output and30seconds; normalized long edge is at most2000pixels. Corrupt/truncated/oversized input fails. These bounds are implementation choices, not recovered user requirements.

Normalization preserves multi-frame order, applies EXIF orientation, flattens transparency on white, converts to RGB and strips output metadata. Original uploaded bytes remain unchanged. Provenance binds original hash/page/orientation/raw dimensions and normalized raster hash/dimensions; coordinates refer to normalized pixels, not invented original-file byte offsets. TIFF raw dimensions are read from tags256/257 because Pillow may already report an oriented size before load; a native orientation6/8 multi-page regression verifies both directions with independent pixel comparisons.

The Python worker uses fixed file arguments and a bounded output protocol. The Node wrapper validates geometry/counts/hash/size, refuses symlink outputs, and cleans private temporary files on success/failure/cancellation. Native tests also verify resizing, white alpha pixels and metadata removal. Animation timing, colour-profile fidelity and rendered-document layout are not inferred. Runtime qualification, byte-bound installation, shared admission, OCR orchestration and public routes remain pending; this factory itself does not provide the required systemd sandbox.
